43 个术语
01

Agent Harness / DSH（智能体运行框架） agent harness

把模型、工具、会话、上下文和插件树装配起来的运行时；DSH 本身不是模型。

总览
官方 / 仓库定义

仓库 README/architecture：DeepSeek Harness 是开源 agent harness，基于 everything-is-a-plugin 的 Cordis；Web/Desktop/CLI/SDK/ACP 共用同一套 base 与 core。

用途

让模型具备可组合的工具、持久会话、上下文管理、权限/沙箱和多载体交付能力。

原理

Cordis 插件树提供服务；Agent Loop 驱动模型/工具；Session 日志作为事实源；profile/bundle 负责装配。

作用范围

Harness 包含运行时与编排层，不等于模型、UI 或单个 Agent；具体供应商/工具通过扩展点接入。

在 DSH 里

仓库根 README；docs/architecture.md；apps/cli；packages/core；packages/bundle。

常见混淆

把 DSH 当成一个模型或聊天壳；它是运行时/装配框架。

最小验证

读 docs/architecture.md 并运行 dsh --profile web --dump-config。

02

Turn（轮） turn

一次被接纳输入的完整排空过程，从 turn/start 到 turn/end。

执行
官方 / 仓库定义

DSH glossary（docs/glossary.md#loop-hierarchy）：one drain of admitted input in a session, ending after the model and its tools stop or a terminal policy intervenes.

用途

把一次用户可见请求与中间的多次模型/工具往返包成一个可取消、可审计、可恢复的生命周期。

原理

Agent Loop 在空闲时从 inbox 取输入，开启 turn；内部按 step 循环；完成、取消或失败都写 turn/end。

作用范围

一个 turn 含 0..N 个 step；不同 turn 之间有 turn/end 边界；它不是单次模型请求。

在 DSH 里

packages/core/agent-loop/src/agent.ts 的 turn()；Session 事件 turn/start、turn/end。

常见混淆

把 turn 当成一次 LLM 请求；实际一次请求只是 step。

最小验证

在 Session 日志里数 turn/start 与 step/start；一个 turn 可以有多条 step/start。

03

Step（步） step

一次模型请求及其引发的工具执行；turn 的下一层调度单位。

执行
官方 / 仓库定义

DSH glossary（docs/glossary.md#loop-hierarchy）：one model request plus the tool executions caused by its response; a turn contains zero or more steps.

用途

把“请求模型 + 执行它要求的工具”作为可重试、可中断、可观测的最小单元。

原理

组装 prompt/tool schema → 请求 → 流式 assistant → 工具调用 → 工具结果 → step/end；有工具结果或新输入时进入下一个 step。

作用范围

一个 step 只对应一次模型请求；工具阶段属于该 step；step 不等于工具调用。

在 DSH 里

agent-loop/src/agent.ts 的 step()；step/start、step/end、tool/call、tool/result 事件。

常见混淆

把 step 当成“一次工具调用”；一个 step 可以没有工具，也可以有多个工具调用。

最小验证

观察 turn/start → step/start → tool/call → tool/result → step/end 的顺序。

04

Session（会话） session

一次对话的 append-only 事件日志，是恢复、回放和投影的事实源。

持久化
官方 / 仓库定义

仓库定义（按 packages/core/session 与 docs/architecture.md 归纳）：由 Session 服务管理的持久化事件历史，带 SessionId、序号和格式版本。

用途

让模型消息、工具历史、生命周期和 UI 投影都能从同一份日志重建。

原理

Session.append 写入类型化事件；deriveMessages 从事件生成模型消息；persistence 写 JSONL，query/projection 建读模型。

作用范围

Session 是会话事实，不是项目/工作目录；一个 Agent 绑定一个 Session，子 Agent 有独立 Session。

在 DSH 里

packages/core/session；packages/session/session-persistence-jsonl；packages/session/session-projection。

常见混淆

把 Session 当成 workspace 或前端 store；Session 是日志，workspace 是文件系统/项目范围。

最小验证

查看会话 .jsonl；用 snapshotEvents() 断言事件序列。

05

SessionEvent 与 model-visible ⟺ logged session event / logged invariant

任何进入模型请求的内容都必须能从 Session 日志重建；日志专用事件不进入模型上下文。

持久化
官方 / 仓库定义

仓库不变式（docs/architecture.md）：模型可见的输入必须可从 Session 日志重建；log-only 事件由 deriveMessages 忽略。

用途

保证恢复、回放、压缩、审计、fork 不会悄悄改变模型看到的内容。

原理

事件是持久化事实；模型消息由读取路径派生；payload 必须是可 JSON 持久化的值；log-only 事件只服务 UI/审计。

作用范围

适用于 prompt/context 注入、工具结果、请求头等模型可见内容；纯 UI 临时状态不必写日志。

在 DSH 里

packages/core/session/src/types.ts；known-event-types.ts；agent-loop 的 derive/prepare 路径。

常见混淆

只在内存里拼一段 prompt、不写事件；刷新或恢复后模型看到的内容会变。

最小验证

恢复同一 Session 后重新 deriveMessages，比较请求头和消息是否一致。

06

Profile（配置档） profile

位于 $DSH_HOME/profiles/<name>/ 的命名运行配置，选择 bundle 并叠加自己的 patch。

装配
官方 / 仓库定义

仓库定义（按 apps/cli 与 packages/boot 归纳）：profile 目录包含 package.json（dsh.profile.bundles 有序列表）与 cordis.patch.yml（用户覆盖层）。

用途

让同一套代码以 web、desktop、headless、SDK 等不同组合运行，而不复制核心。

原理

CLI --profile 选择目录；app-boot 读取 bundle 列表，按顺序合并 patch；最后应用 profile patch 和命令行 overlay。

作用范围

Profile 是装配结果，不是用户设置页面；一个进程加载一个 profile；它不等于 npm package。

在 DSH 里

apps/cli/src/profile-boot.ts；packages/boot/app-boot/src/profile.ts；~/.dsh/profiles/<name>/。

常见混淆

把 Profile 当成“用户偏好设置”或“插件包”；它是运行配置组合。

最小验证

dsh --profile web --dump-config，查看最终组合树。

07

Bundle（配置束） bundle

以 npm 包分发的一组 Cordis 配置行，通过 package.json 的 dsh.bundle 指向 patch 文件。

装配
官方 / 仓库定义

仓库定义（packages/bundle/README.md）：bundle 提供可复用的配置行，profile 按需选择并按顺序应用。

用途

把共享底座（base）、载体（web-app/headless）和配置从核心代码中解耦，便于组合与发布。

原理

bundle 的 cordis.patch.yml 用 insert/update/remove 行描述树；应用后行进入 Loader 配置。

作用范围

Bundle 是配置分发单位，不是运行中的插件实例；一个 profile 可加载多个 bundle。

在 DSH 里

packages/bundle/base、web-app、headless、sdk-app、acp-app 的 cordis.patch.yml。

常见混淆

把 Bundle 等同于 npm 包本身；npm 包只是载体，bundle 是其中的配置入口。

最小验证

查看 package.json 的 dsh.bundle 字段和 patch 内容。

08

Patch / Overlay（覆盖层） patch / overlay

按 id 定位 Cordis 行的 YAML 覆盖层；后写覆盖前写，config 整段替换。

装配
官方 / 仓库定义

仓库定义（packages/bundle/*/cordis.patch.yml 与 docs/architecture.md）：patch 通过 id 覆盖目标行；不是深合并。

用途

在不改上游代码的情况下替换/调整配置，支持 profile 定制和命令行实验。

原理

多个 patch 按 bundle → profile → user → CLI 顺序合成；同 id 最后写入者生效；行内 config 被完整替换。

作用范围

只影响目标 id 行；未写的字段不会从旧层继承；覆盖不等于新增插件代码。

在 DSH 里

bundle patch、profile 的 cordis.patch.yml、$DSH_HOME/cordis.patch.yml、--patch 参数。

常见混淆

以为 config 会深合并；实际整段替换，所以覆盖层要写全字段。

最小验证

用 --dump-config 比较覆盖前后的同一行。

09

Loader（加载器） loader

Cordis 的配置加载器：解析行、按服务可用性与 inject 激活插件、管理 fiber 生命周期。

装配
官方 / 仓库定义

仓库定义（vendor/cordis + app-boot）：Loader 驱动 Cordis 插件树直到稳定；激活顺序由依赖/服务可用性决定。

用途

把静态 patch 变成运行中的服务图，并支持 HMR/卸载。

原理

Loader 读取配置行，创建插件 fiber；插件声明 inject，等待服务出现；注册通过 effect 回滚。

作用范围

Loader 不按 YAML 行顺序加载；配置覆盖在加载前已经完成；它不等于插件代码本身。

在 DSH 里

vendor/cordis；@deepseek-ai/cordis-plugin-loader；packages/boot/app-boot/src/index.ts。

常见混淆

认为行顺序就是启动顺序；实际是由服务可用性驱动。

最小验证

看 Loader 日志/启动顺序；在 dump-config 中观察 inject 依赖。

10

Plugin（插件） plugin

可加载/卸载的 Cordis 模块，通常导出 name、inject、Config、apply；服务包可默认导出服务类。

组合
官方 / 仓库定义

仓库约定（packages/AGENTS.md）：函数插件命名导出 name/inject/Config/apply，服务包默认导出服务类；混合形式会让 Loader 丢弃命名空间。

用途

把能力拆成可组合、可替换、可回滚的单元。

原理

Loader 调用 apply(ctx, config)；插件在 ctx 上注册服务、工具、监听器；fiber 卸载时 effect 回滚。

作用范围

一个插件可注册多个能力；插件不等于 Service，也不等于 Tool。

在 DSH 里

packages/*/*/src/index.ts；apps/desktop-host；packages/client/ui-*。

常见混淆

把 Plugin 等同于 Tool；工具只是插件可能注册的一个模型能力。

最小验证

加载/卸载插件，观察服务或工具是否随之出现/消失。

11

Service（服务） service

挂在 ctx 上的共享能力对象，例如 ctx.tools、ctx.sessions、ctx.llm。

组合
官方 / 仓库定义

仓库定义（Cordis + docs/architecture.md）：服务是插件之间通过 ctx 使用的能力接口，由 Service Definition/Provider/Consumer 构成能力接缝。

用途

让插件通过能力接口解耦，而不是互相 import 具体实现。

原理

Provider 注册服务；Consumer 通过 inject 声明依赖并使用 ctx.<service>；服务生命周期随 fiber/effect 管理。

作用范围

服务是共享能力；Tool 是服务的一种消费者/注册项；Service 不等于 Plugin。

在 DSH 里

ctx.tools、ctx.llm、ctx.sessions、ctx.shell、ctx.fs、ctx.sandbox。

常见混淆

把 Service 当成某个具体工具或插件；服务是能力接口/对象。

最小验证

在插件的 inject 中声明服务；dump-config 查看依赖。

12

Capability Seam（能力接缝） capability seam

一个可替换能力的三角色整体：Service Definition、Provider、Consumer。

组合
官方 / 仓库定义

DSH glossary（docs/glossary.md#capability-seam）：seam 是带三角色的可替换能力；它永远不是单个角色，保留给完整能力使用。

用途

在不改 Consumer 的前提下替换 Provider，并把策略/平台差异隔离在能力边界。

原理

Definition 定义服务与语义；Provider 实现平台/后端；Consumer 注入服务；Loader 按可用性装配。

作用范围

适用于可替换能力（shell、sandbox、fs、llm 等）；不是任何 interface 或任意依赖都叫 seam。

在 DSH 里

packages/shell（Definition）、bash-local/bash-sandbox（Providers）、tool-bash（Consumer）。

常见混淆

把 seam 说成单个 Service/interface；seam 是完整能力，单个角色应叫 Definition/Provider/Consumer。

最小验证

画出一个能力的 Definition/Provider/Consumer 三角色，并替换 Provider 跑测试。

13

Effect / Disposer（副作用与清理） effect / disposer

由 ctx.effect() 管理的注册副作用；返回 disposer，插件卸载时自动回滚。

组合
官方 / 仓库定义

仓库定义（Cordis 插件约定）：注册服务、工具、监听器、UI 槽位等应通过 effect 或注册返回的 disposer 管理。

用途

避免重复注册、泄漏和热更新残留，保证卸载可逆。

原理

effect 绑定到当前 fiber/plugin 生命周期；dispose 时按注册清理；ctx.on/register 通常返回 disposer。

作用范围

所有需要回滚的注册；不是业务事务，也不保证跨进程/持久化回滚。

在 DSH 里

vendor/cordis 的 ctx.effect；各插件的 ctx.on/register。

常见混淆

认为手动 removeListener 就足够；异常路径、重复注册和 HMR 容易漏清理。

最小验证

dispose 插件后确认工具/服务/监听器消失；HMR 安全测试。

14

Tool（工具） tool

模型可调用的动作：name、description、参数 schema、execute、output/presentation。

能力
官方 / 仓库定义

仓库定义（packages/core/tools/README.md）：defineTool 声明类型化参数、输出契约、执行体和可选 UI 呈现；工具注册到 ctx.tools。

用途

把文件、终端、网络、数据库等实际动作以受控 schema 暴露给模型。

原理

模型产生 tool call → registry 校验/权限/执行 → 结果写 tool/result → 模型看到结果；native 或 PTC 两种呈现。

作用范围

Tool 是模型接口；具体能力由 Provider/Service 实现；Tool 不是 Plugin/Service。

在 DSH 里

packages/core/tools；packages/fs/tool-fs；packages/shell/tool-bash；packages/web/tool-web。

常见混淆

把 Tool 当成后端函数或插件；工具只是模型可见的动作接口。

最小验证

注册后 dump-config 看到 schema；调用产生 tool/call 与 tool/result。

15

Tool Registry（工具注册表） tool registry

ctx.tools：保存工具定义、可见性、权限与执行，并把 schema 喂给 prompt 组装。

能力
官方 / 仓库定义

仓库定义（packages/core/tools）：注册即让工具对 Agent 可见；registry 负责 schema、校验、策略、执行和结果封装。

用途

集中管理工具生命周期、可见性、权限、并发和呈现，避免 loop 里散落工具逻辑。

原理

register 注册；restrict 按 scope 过滤；pre/post 管线；native/PTC 执行；结果进入 Session。

作用范围

每个 Agent scope 可有不同可见性/限制；registry 不是 UI 列表，也不是业务实现。

在 DSH 里

packages/core/tools/src/index.ts；agent-loop/src/tool-calls.ts。

常见混淆

把 registry 当成静态工具清单；它同时管执行/策略/呈现。

最小验证

注册、restrict、dispose，检查 prompt schema 与执行结果。

16

Skill（技能） skill

可加载的指令/脚本知识包，通常通过 skill 工具读取；不是模型可直接执行的动作。

能力
官方 / 仓库定义

仓库定义（packages/skill）：skill 提供领域流程/知识，由 tool-skill 读取；Office 等 skill 还会提供 CLI 路径。

用途

把可复用流程和领域知识注入上下文，而不是把每种流程写进 agent-loop。

原理

发现/读取 skill 内容 → 作为工具结果/上下文进入模型 → 模型按流程调用现有 tools/shell。

作用范围

Skill 内容通常模型可见；实际执行仍通过 tools/shell；skill 不是权限边界。

在 DSH 里

packages/skill/skill-filesystem；skill-office；tool-skill。

常见混淆

把 Skill 当成 Tool/function；skill 是知识/流程，tool 是动作。

最小验证

调用 skill 工具，查看返回内容/Office CLI 路径。

17

Host（宿主进程） host

运行 Cordis 插件树、Agent、Session、工具和 Web API 的 Node 进程。

载体
官方 / 仓库定义

仓库定义（docs/architecture.md）：Web Host 与 Desktop Host 是不同载体，但都运行同一套 Host/插件树。

用途

承载有状态运行时；让 Client 只做投影和交互。

原理

app-boot/Loader 装配树；webServer 提供 HTTP/WS；Agent/Session/Tools 在进程内运行。

作用范围

Host 不是 Electron main，也不是浏览器；一个 Host 进程通常服务一个 profile。

在 DSH 里

packages/bundle/web-app；packages/host/webserver；apps/desktop-host。

常见混淆

把 Host 当成 Web 服务器或 UI；Host 是运行时。

最小验证

dsh web 启动后看进程、端口和日志；Client 只是连接方。

18

Client（客户端） client

浏览器/Electron 渲染层，通过 HTTP/WS 消费 Host 投影；UI 插件位于 packages/client/ui-*。

载体
官方 / 仓库定义

仓库定义（packages/client）：Client 通过 API/WS 发命令、订阅投影、渲染 UI；不直接运行 Agent。

用途

把交互与运行时分离，使 Web、Desktop 复用同一套 Host。

原理

Client 插件注册槽位/状态；Host 广播投影；用户操作转成 API 命令。

作用范围

Client 不读 Host 文件系统、不直接跑模型；它不是 Agent 的一部分。

在 DSH 里

packages/client；apps/web；apps/desktop 的 preload/renderer。

常见混淆

把 Client 当成 Host 的一部分；禁用 Client 后 Host 仍可 headless/SDK 运行。

最小验证

停掉浏览器仍可通过 CLI/SDK 驱动同一 Host。

19

Desktop Host（桌面宿主） desktop host

桌面版实际运行 Host 的 Node 子进程；Electron main 通过 IPC 启动/管理它。

载体
官方 / 仓库定义

仓库定义（apps/desktop-host）：Electron 以 ELECTRON_RUN_AS_NODE 启动 Desktop Host，加载 desktop profile，复用 Web Host 与插件树。

用途

把有状态 Host 与 Electron 壳隔离，避免把插件树塞进主进程，同时复用 Web 运行时。

原理

Electron main 创建窗口/协议 → spawn Desktop Host → Host 监听 Web/API → IPC boot/ready 把 token/端口交给页面。

作用范围

Desktop Host 不是 Electron main，也不是独立 Agent 实现；它负责 Office/更新/退出等桌面能力。

在 DSH 里

apps/desktop-host/src/index.ts；apps/desktop/src/main.ts；desktop profile patch。

常见混淆

把 Electron main 当 Host；main 只是壳，Host 是 Node 子进程。

最小验证

看进程树：Electron main + Desktop Host；日志出现 dsh web 地址。

20

Primary Runtime（主运行时） primary runtime

打包进 Desktop 的独立 Node/Python/pnpm/依赖运行时，位于 resources/runtime/primary-runtime。

载体
官方 / 仓库定义

仓库定义（scripts/primary-runtime）：lock.json 固定 Node/Python/pnpm 版本与哈希，prepare-runtime 下载、校验并组装。

用途

让用户机器无需预装 Node/Python/pnpm，并保证构建可复现。

原理

lock 记录版本/URL/hash；prepare-runtime 下载/校验；CLI/runtime 从打包目录解析解释器。

作用范围

只包含受控运行时；不等于系统工具链；Office/Python 依赖也随 runtime 打包。

在 DSH 里

scripts/primary-runtime/lock.json；apps/desktop/scripts/prepare-runtime.ts；resources/runtime/versions.json。

常见混淆

依赖用户系统的 node/python；桌面版用自己的 primary runtime。

最小验证

查看 resources/runtime/versions.json；dsh --version 正常。

21

Sandbox（沙箱） sandbox

对进程/文件访问施加限制的策略与实现；Linux 用 bwrap → Landlock，按可用性 fail-closed。

安全
官方 / 仓库定义

仓库定义（packages/sandbox）：dsh-sandbox 是 Service Definition，sandbox-local 提供本地实现，bash/fs 工具是 Consumer。

用途

原理

作用范围

不是完整 VM 安全边界；平台能力不同；工具/provider 仍需做输入校验。

在 DSH 里

packages/sandbox/sandbox；sandbox-local；sandbox-policy；fs-sandbox；bash-sandbox。

常见混淆

把 sandbox 当成 VM/容器；DSH 的本地沙箱是进程/文件策略。

最小验证

触发拒绝，观察 [sandbox: ...] 标记；dump-config 查看 sandbox seam。

Agent Scope（智能体作用域） agent scope

按 Agent 隔离注册的作用域；注册要么全局，要么属于一个 scope key，且不向子 Agent 继承。

组合
官方 / 仓库定义

DSH glossary（docs/glossary.md#agent-scope）：scope 是 per-agent registration 的单位；两级、扁平；scoped 注册不会继承给子 Agent。

用途

让不同 Agent 拥有不同工具/提示/监听器，而不污染全局。

原理

scope key 通常是 live agent 对象；agent.ctx 注册 scope-visible+scope-lifetime；dispatch 带 scope carrier。

作用范围

subagent 不自动继承 scope；lineage 只是数据，不改变可见性。

在 DSH 里

packages/core/scope；agent.ctx；agent-preset。

常见混淆

以为子 Agent 自动继承父 Agent 的工具；实际需要显式装配。

最小验证

给父 Agent 注册 scoped tool，创建子 Agent，确认子 Agent 不可见。
