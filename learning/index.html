学习法：三遍法

01

专业术语

先把词用对：Turn、Step、Plugin、Service、Tool、Profile、Bundle、Patch

目标：看到 DSH 的文档、日志或代码时，能准确说出每个词指的是哪一层，不把“插件、服务、工具、bundle”混成一类。

先看速查表建立边界；后半部分有 43 个术语的逐条详解（官方/仓库定义、用途、原理、作用范围、常见混淆、验证）。HTML 版会把它渲染成可搜索卡片。

1. 运行时与执行

术语 一句话定义 在 DSH 里看哪里
Agent harness 驱动模型、工具、会话和上下文的基础设施；本身不是模型 整个仓库
Agent 一次可创建、可恢复、可取消的智能体实例 packages/core/agent
Turn 一轮用户可见的请求；从 turn/start 到 turn/end packages/core/agent-loop
Step 一次模型请求及其后的工具阶段；一个 turn 可以有多 step agent-loop/src/agent.ts 的 step()
Session 一次对话的持久化事实源，通常是 append-only 事件日志 packages/core/session
SessionEvent 写入 Session 的类型化记录，例如 turn/start、tool/result session/src/types.ts 的声明合并
model-visible ⟺ logged 任何进入模型请求的内容，都必须能从 Session 日志重建 docs/architecture.md
Replay 从日志重建消息、工具历史、UI 状态 deriveMessages、Session projection
Inbox Agent 的待处理输入队列；followup/steer/inject 进入不同位置 packages/core/agent-loop/src/inbox.ts

易错：Turn 不是 Step。一个 turn 里模型可以先请求工具，拿到结果后再请求一次；第二次请求是新的 step，不是新的 turn。

2. 组合：Cordis、插件、服务

术语 一句话定义 在 DSH 里看哪里
Cordis DSH 使用的插件/服务/事件运行时 vendor/cordis
Context（ctx） 插件看到的运行时上下文；服务、事件、effect 都挂在它上面 @deepseek-ai/cordis
Plugin 一段可加载/卸载的代码，通常导出 name、inject、Config、apply 各 package 的 src/index.ts
Service 挂在 ctx 上的能力对象，例如 ctx.tools、ctx.sessions、ctx.llm packages/*/*/src/index.ts
Service Definition 定义能力接口和语义的包，不提供具体实现 例如 packages/sandbox/sandbox
Provider 实现某个 Service Definition 的包 例如 packages/sandbox/sandbox-local
Consumer 使用某个服务的包 例如 packages/shell/tool-bash
Capability seam Definition / Provider / Consumer 三角色组成的能力接缝 docs/architecture.md
Effect 由 ctx.effect() 管理的注册，卸载时自动回滚 任何注册服务、工具、监听器的插件
Disposer 注册返回的清理函数；卸载插件或销毁 fiber 时调用 ctx.effect、ctx.on、register

易错：Plugin 不是 Service，也不是 Tool。插件是加载单位；服务是它向 ctx 提供的能力；工具是它注册给模型的能力之一。

3. 装配：Profile、Bundle、Patch

术语 一句话定义 在 DSH 里看哪里
Profile 一个命名运行配置，位于 $DSH_HOME/profiles/<name>，由 package.json 与 patch 文件描述 packages/boot/app-boot/src/profile.ts
Bundle 以 npm 包分发的一组 Cordis 配置行，通过 dsh.bundle 指向 patch packages/bundle/*/cordis.patch.yml
Patch YAML 覆盖层；按 id 定位行，后写覆盖前写 packages/bundle/base/cordis.patch.yml
Loader 读取 Cordis 配置、解析服务依赖并激活插件的运行时 @deepseek-ai/cordis-plugin-loader
Composition 把多个 patch 层合成为最终插件树 composeEntries、prepareProfileEntries
Overlay 叠加的配置层；命令行 --patch 是最后一层 apps/cli/src/profile-boot.ts

装配顺序：bundle patch → profile 的 cordis.patch.yml → $DSH_HOME/cordis.patch.yml → 命令行 --patch；后面的层覆盖前面的同 id 行。

易错：Profile 不是“用户设置”，Bundle 也不是“插件包”的同义词。Profile 是装配结果，Bundle 是可复用的一组配置行。

4. 模型与能力

术语 一句话定义 在 DSH 里看哪里
Tool 模型可调用的能力：有 name、description、参数 schema、execute 和 presentation packages/core/tools、packages/fs/tool-fs
Tool registry 保存工具定义、可见性、权限和执行的注册表 ctx.tools
Tool call / result 模型请求执行工具，以及执行业务返回的结构化结果 Session 的 tool/call、tool/result
Skill 可加载的指令/脚本知识包，通常通过 skill 工具读取 packages/skill、packages/skill/skill-office
MCP 外部工具/资源服务器协议；DSH 通过 MCP client 接入 packages/mcp/mcp-client
Subagent 由主 Agent 派生、拥有自己 Session 的子智能体 packages/subagent
Workflow 由多个节点/工具步骤组成的编排能力 packages/workflow
PTC Programmatic Tool Calling；模型写程序调用工具，而不是逐条 function call packages/ptc-runtime
Compaction 压缩上下文，控制 token 预算 packages/compaction
Sandbox 对进程/文件访问做限制的策略与实现 packages/sandbox

易错：Skill 通常不是 Tool。Tool 是模型可直接调用的动作；Skill 是一段被读取/加载的知识或流程，可能再调用工具。

5. 载体与界面

术语 一句话定义 在 DSH 里看哪里
Host 运行 Cordis 插件树和 Session 的 Node 进程 packages/bundle/web-app、apps/desktop-host
Client 浏览器/Electron 渲染层，通过 HTTP/WS 投影 Host 状态 packages/client
Web Host 提供 HTTP/WS、API gateway、静态前端的 Host 能力 packages/host/webserver、packages/api/gateway
Desktop Host 桌面版实际运行 Host 的子进程，不是 Electron main apps/desktop-host
Electron shell 只负责窗口、菜单、协议、目录选择等壳能力 apps/desktop/src/main.ts
Primary runtime 打包进桌面的 Node/Python/pnpm 解释器与依赖 apps/desktop/scripts/prepare-runtime.ts
Headless 不启动 UI 的一次性 CLI 运行 profile packages/bundle/headless
ACP 通过 stdio 接入的自动化协议载体 packages/bundle/acp-app
SDK TypeScript/Python 远程调用 Host 的客户端 packages/sdk、python/sdk-runtime

易错：Desktop 不是另一套 harness。它只是 Electron 壳 + 私有 Desktop Host + 同一个 Web Host；核心插件树与 Web 版共用。

6. 持久化与验证

术语 一句话定义 在 DSH 里看哪里
Session format version Session 日志的兼容代际；只在新 reader 无法安全解释旧记录时递增 packages/core/session/src/types.ts
Persistence 把 Session 事件写入磁盘/数据库的实现 packages/session/session-persistence-jsonl
Projection 从事件日志派生列表、标题、统计等读模型 packages/session/session-projection
Snapshot 录制后回放的期望输出，用于 keyless 测试 packages/test-support/session-snapshot
Fixture 测试输入或固定数据 各 package 的 tests/fixtures
Smoke 打包后跑真实进程的最小验收，不是单元测试 apps/desktop/scripts/smoke-runtime.ts

易错：Projection 不是事实源；它从 Session 日志派生。日志才是可以重放的事实。

43 个术语
01

Agent Harness / DSH（智能体运行框架） agent harness

把模型、工具、会话、上下文和插件树装配起来的运行时；DSH 本身不是模型。

总览
官方 / 仓库定义

仓库 README/architecture：DeepSeek Harness 是开源 agent harness，基于 everything-is-a-plugin 的 Cordis；Web/Desktop/CLI/SDK/ACP 共用同一套 base 与 core。

用途

让模型具备可组合的工具、持久会话、上下文管理、权限/沙箱和多载体交付能力。

原理

Cordis 插件树提供服务；Agent Loop 驱动模型/工具；Session 日志作为事实源；profile/bundle 负责装配。

作用范围

Harness 包含运行时与编排层，不等于模型、UI 或单个 Agent；具体供应商/工具通过扩展点接入。

在 DSH 里

仓库根 README；docs/architecture.md；apps/cli；packages/core；packages/bundle。

常见混淆

把 DSH 当成一个模型或聊天壳；它是运行时/装配框架。

最小验证

读 docs/architecture.md 并运行 dsh --profile web --dump-config。

02

Turn（轮） turn

一次被接纳输入的完整排空过程，从 turn/start 到 turn/end。

执行
官方 / 仓库定义

DSH glossary（docs/glossary.md#loop-hierarchy）：one drain of admitted input in a session, ending after the model and its tools stop or a terminal policy intervenes.

用途

把一次用户可见请求与中间的多次模型/工具往返包成一个可取消、可审计、可恢复的生命周期。

原理

Agent Loop 在空闲时从 inbox 取输入，开启 turn；内部按 step 循环；完成、取消或失败都写 turn/end。

作用范围

一个 turn 含 0..N 个 step；不同 turn 之间有 turn/end 边界；它不是单次模型请求。

在 DSH 里

packages/core/agent-loop/src/agent.ts 的 turn()；Session 事件 turn/start、turn/end。

常见混淆

把 turn 当成一次 LLM 请求；实际一次请求只是 step。

最小验证

在 Session 日志里数 turn/start 与 step/start；一个 turn 可以有多条 step/start。

03

Step（步） step

一次模型请求及其引发的工具执行；turn 的下一层调度单位。

执行
官方 / 仓库定义

DSH glossary（docs/glossary.md#loop-hierarchy）：one model request plus the tool executions caused by its response; a turn contains zero or more steps.

用途

把“请求模型 + 执行它要求的工具”作为可重试、可中断、可观测的最小单元。

原理

组装 prompt/tool schema → 请求 → 流式 assistant → 工具调用 → 工具结果 → step/end；有工具结果或新输入时进入下一个 step。

作用范围

一个 step 只对应一次模型请求；工具阶段属于该 step；step 不等于工具调用。

在 DSH 里

agent-loop/src/agent.ts 的 step()；step/start、step/end、tool/call、tool/result 事件。

常见混淆

把 step 当成“一次工具调用”；一个 step 可以没有工具，也可以有多个工具调用。

最小验证

观察 turn/start → step/start → tool/call → tool/result → step/end 的顺序。

04

Session（会话） session

一次对话的 append-only 事件日志，是恢复、回放和投影的事实源。

持久化
官方 / 仓库定义

仓库定义（按 packages/core/session 与 docs/architecture.md 归纳）：由 Session 服务管理的持久化事件历史，带 SessionId、序号和格式版本。

用途

让模型消息、工具历史、生命周期和 UI 投影都能从同一份日志重建。

原理

Session.append 写入类型化事件；deriveMessages 从事件生成模型消息；persistence 写 JSONL，query/projection 建读模型。

作用范围

Session 是会话事实，不是项目/工作目录；一个 Agent 绑定一个 Session，子 Agent 有独立 Session。

在 DSH 里

packages/core/session；packages/session/session-persistence-jsonl；packages/session/session-projection。

常见混淆

把 Session 当成 workspace 或前端 store；Session 是日志，workspace 是文件系统/项目范围。

最小验证

查看会话 .jsonl；用 snapshotEvents() 断言事件序列。

05

SessionEvent 与 model-visible ⟺ logged session event / logged invariant

任何进入模型请求的内容都必须能从 Session 日志重建；日志专用事件不进入模型上下文。

持久化
官方 / 仓库定义

仓库不变式（docs/architecture.md）：模型可见的输入必须可从 Session 日志重建；log-only 事件由 deriveMessages 忽略。

用途

保证恢复、回放、压缩、审计、fork 不会悄悄改变模型看到的内容。

原理

事件是持久化事实；模型消息由读取路径派生；payload 必须是可 JSON 持久化的值；log-only 事件只服务 UI/审计。

作用范围

适用于 prompt/context 注入、工具结果、请求头等模型可见内容；纯 UI 临时状态不必写日志。

在 DSH 里

packages/core/session/src/types.ts；known-event-types.ts；agent-loop 的 derive/prepare 路径。

常见混淆

只在内存里拼一段 prompt、不写事件；刷新或恢复后模型看到的内容会变。

最小验证

恢复同一 Session 后重新 deriveMessages，比较请求头和消息是否一致。

06

Profile（配置档） profile

位于 $DSH_HOME/profiles/<name>/ 的命名运行配置，选择 bundle 并叠加自己的 patch。

装配
官方 / 仓库定义

仓库定义（按 apps/cli 与 packages/boot 归纳）：profile 目录包含 package.json（dsh.profile.bundles 有序列表）与 cordis.patch.yml（用户覆盖层）。

用途

让同一套代码以 web、desktop、headless、SDK 等不同组合运行，而不复制核心。

原理

CLI --profile 选择目录；app-boot 读取 bundle 列表，按顺序合并 patch；最后应用 profile patch 和命令行 overlay。

作用范围

Profile 是装配结果，不是用户设置页面；一个进程加载一个 profile；它不等于 npm package。

在 DSH 里

apps/cli/src/profile-boot.ts；packages/boot/app-boot/src/profile.ts；~/.dsh/profiles/<name>/。

常见混淆

把 Profile 当成“用户偏好设置”或“插件包”；它是运行配置组合。

最小验证

dsh --profile web --dump-config，查看最终组合树。

07

Bundle（配置束） bundle

以 npm 包分发的一组 Cordis 配置行，通过 package.json 的 dsh.bundle 指向 patch 文件。

装配
官方 / 仓库定义

仓库定义（packages/bundle/README.md）：bundle 提供可复用的配置行，profile 按需选择并按顺序应用。

用途

把共享底座（base）、载体（web-app/headless）和配置从核心代码中解耦，便于组合与发布。

原理

bundle 的 cordis.patch.yml 用 insert/update/remove 行描述树；应用后行进入 Loader 配置。

作用范围

Bundle 是配置分发单位，不是运行中的插件实例；一个 profile 可加载多个 bundle。

在 DSH 里

packages/bundle/base、web-app、headless、sdk-app、acp-app 的 cordis.patch.yml。

常见混淆

把 Bundle 等同于 npm 包本身；npm 包只是载体，bundle 是其中的配置入口。

最小验证

查看 package.json 的 dsh.bundle 字段和 patch 内容。

08

Patch / Overlay（覆盖层） patch / overlay

按 id 定位 Cordis 行的 YAML 覆盖层；后写覆盖前写，config 整段替换。

装配
官方 / 仓库定义

仓库定义（packages/bundle/*/cordis.patch.yml 与 docs/architecture.md）：patch 通过 id 覆盖目标行；不是深合并。

用途

在不改上游代码的情况下替换/调整配置，支持 profile 定制和命令行实验。

原理

多个 patch 按 bundle → profile → user → CLI 顺序合成；同 id 最后写入者生效；行内 config 被完整替换。

作用范围

只影响目标 id 行；未写的字段不会从旧层继承；覆盖不等于新增插件代码。

在 DSH 里

bundle patch、profile 的 cordis.patch.yml、$DSH_HOME/cordis.patch.yml、--patch 参数。

常见混淆

以为 config 会深合并；实际整段替换，所以覆盖层要写全字段。

最小验证

用 --dump-config 比较覆盖前后的同一行。

09

Loader（加载器） loader

Cordis 的配置加载器：解析行、按服务可用性与 inject 激活插件、管理 fiber 生命周期。

装配
官方 / 仓库定义

仓库定义（vendor/cordis + app-boot）：Loader 驱动 Cordis 插件树直到稳定；激活顺序由依赖/服务可用性决定。

用途

把静态 patch 变成运行中的服务图，并支持 HMR/卸载。

原理

Loader 读取配置行，创建插件 fiber；插件声明 inject，等待服务出现；注册通过 effect 回滚。

作用范围

Loader 不按 YAML 行顺序加载；配置覆盖在加载前已经完成；它不等于插件代码本身。

在 DSH 里

vendor/cordis；@deepseek-ai/cordis-plugin-loader；packages/boot/app-boot/src/index.ts。

常见混淆

认为行顺序就是启动顺序；实际是由服务可用性驱动。

最小验证

看 Loader 日志/启动顺序；在 dump-config 中观察 inject 依赖。

10

Plugin（插件） plugin

可加载/卸载的 Cordis 模块，通常导出 name、inject、Config、apply；服务包可默认导出服务类。

组合
官方 / 仓库定义

仓库约定（packages/AGENTS.md）：函数插件命名导出 name/inject/Config/apply，服务包默认导出服务类；混合形式会让 Loader 丢弃命名空间。

用途

把能力拆成可组合、可替换、可回滚的单元。

原理

Loader 调用 apply(ctx, config)；插件在 ctx 上注册服务、工具、监听器；fiber 卸载时 effect 回滚。

作用范围

一个插件可注册多个能力；插件不等于 Service，也不等于 Tool。

在 DSH 里

packages/*/*/src/index.ts；apps/desktop-host；packages/client/ui-*。

常见混淆

把 Plugin 等同于 Tool；工具只是插件可能注册的一个模型能力。

最小验证

加载/卸载插件，观察服务或工具是否随之出现/消失。

11

Service（服务） service

挂在 ctx 上的共享能力对象，例如 ctx.tools、ctx.sessions、ctx.llm。

组合
官方 / 仓库定义

仓库定义（Cordis + docs/architecture.md）：服务是插件之间通过 ctx 使用的能力接口，由 Service Definition/Provider/Consumer 构成能力接缝。

用途

让插件通过能力接口解耦，而不是互相 import 具体实现。

原理

Provider 注册服务；Consumer 通过 inject 声明依赖并使用 ctx.<service>；服务生命周期随 fiber/effect 管理。

作用范围

服务是共享能力；Tool 是服务的一种消费者/注册项；Service 不等于 Plugin。

在 DSH 里

ctx.tools、ctx.llm、ctx.sessions、ctx.shell、ctx.fs、ctx.sandbox。

常见混淆

把 Service 当成某个具体工具或插件；服务是能力接口/对象。

最小验证

在插件的 inject 中声明服务；dump-config 查看依赖。

12

Capability Seam（能力接缝） capability seam

一个可替换能力的三角色整体：Service Definition、Provider、Consumer。

组合
官方 / 仓库定义

DSH glossary（docs/glossary.md#capability-seam）：seam 是带三角色的可替换能力；它永远不是单个角色，保留给完整能力使用。

用途

在不改 Consumer 的前提下替换 Provider，并把策略/平台差异隔离在能力边界。

原理

Definition 定义服务与语义；Provider 实现平台/后端；Consumer 注入服务；Loader 按可用性装配。

作用范围

适用于可替换能力（shell、sandbox、fs、llm 等）；不是任何 interface 或任意依赖都叫 seam。

在 DSH 里

packages/shell（Definition）、bash-local/bash-sandbox（Providers）、tool-bash（Consumer）。

常见混淆

把 seam 说成单个 Service/interface；seam 是完整能力，单个角色应叫 Definition/Provider/Consumer。

最小验证

画出一个能力的 Definition/Provider/Consumer 三角色，并替换 Provider 跑测试。

13

Effect / Disposer（副作用与清理） effect / disposer

由 ctx.effect() 管理的注册副作用；返回 disposer，插件卸载时自动回滚。

组合
官方 / 仓库定义

仓库定义（Cordis 插件约定）：注册服务、工具、监听器、UI 槽位等应通过 effect 或注册返回的 disposer 管理。

用途

避免重复注册、泄漏和热更新残留，保证卸载可逆。

原理

effect 绑定到当前 fiber/plugin 生命周期；dispose 时按注册清理；ctx.on/register 通常返回 disposer。

作用范围

所有需要回滚的注册；不是业务事务，也不保证跨进程/持久化回滚。

在 DSH 里

vendor/cordis 的 ctx.effect；各插件的 ctx.on/register。

常见混淆

认为手动 removeListener 就足够；异常路径、重复注册和 HMR 容易漏清理。

最小验证

dispose 插件后确认工具/服务/监听器消失；HMR 安全测试。

Tool（工具） tool

模型可调用的动作：name、description、参数 schema、execute、output/presentation。

能力
官方 / 仓库定义

仓库定义（packages/core/tools/README.md）：defineTool 声明类型化参数、输出契约、执行体和可选 UI 呈现；工具注册到 ctx.tools。

用途

作用范围

Tool 是模型接口；具体能力由 Provider/Service 实现；Tool 不是 Plugin/Service。

在 DSH 里

packages/core/tools；packages/fs/tool-fs；packages/shell/tool-bash；packages/web/tool-web。

常见混淆

把 Tool 当成后端函数或插件；工具只是模型可见的动作接口。

最小验证

注册后 dump-config 看到 schema；调用产生 tool/call 与 tool/result。

Tool Registry（工具注册表） tool registry

ctx.tools：保存工具定义、可见性、权限与执行，并把 schema 喂给 prompt 组装。

能力
官方 / 仓库定义

仓库定义（packages/core/tools）：注册即让工具对 Agent 可见；registry 负责 schema、校验、策略、执行和结果封装。

用途

集中管理工具生命周期、可见性、权限、并发和呈现，避免 loop 里散落工具逻辑。

原理

作用范围

每个 Agent scope 可有不同可见性/限制；registry 不是 UI 列表，也不是业务实现。

在 DSH 里

packages/core/tools/src/index.ts；agent-loop/src/tool-calls.ts。

常见混淆

把 registry 当成静态工具清单；它同时管执行/策略/呈现。

最小验证

注册、restrict、dispose，检查 prompt schema 与执行结果。

载体

Sandbox（沙箱） sandbox

安全

Projection（投影） projection

从 Session 事件派生的读模型（列表、标题、统计、UI 状态），不是事实源。

持久化
官方 / 仓库定义

仓库定义（packages/session/session-projection）：projection 从事件日志派生，可重建；日志才是事实。

用途

让查询/渲染高效，避免每次重放全部日志。

监听事件增量更新；从日志重建；缓存/数据库可丢弃。

作用范围

在 DSH 里

packages/session/session-projection；client store 中的派生状态。

常见混淆

把投影数据库当主库；删掉投影后必须能从日志恢复。

最小验证

删除/重建 projection，Session 日志与模型上下文不受影响。

Compaction（上下文压缩） compaction

压缩上下文以控制 token 预算的插件集合，例如基础压缩、图片卸载、工具结果裁剪。

持久化

长会话后检查请求消息变短、日志仍完整。

Subagent（子智能体） subagent

Agent（智能体） agent

一个可创建、恢复、取消的 live agent；有独立 Session 和控制面。

执行
官方 / 仓库定义

给插件、UI 和编排器一个稳定的控制面，而不是直接操作 loop 内部状态。

在 DSH 里

packages/core/agent；packages/core/agent-loop；ctx.agents。

常见混淆

把 Agent 当成模型调用或 Session；Agent 是控制面+运行时对象。

创建 Agent → followup → whenIdle；查看 agent/created、turn/start、agent/disposed。

Inbox（输入队列） inbox

执行

在 DSH 里

agent-loop/src/inbox.ts；AgentHandle.followup/steer/inject。

常见混淆

把 inject 当成 followup；inject 不唤醒 driver。

最小验证

运行中 steer/inject，观察 step 边界与 agent/inbox 事件。

Workspace（工作区） workspace

Model Provider / Adapter（模型适配器） model provider / adapter

把 DSH 的统一 LLM 请求映射到具体供应商 API 的适配器，负责流式、工具调用和错误语义。

packages/llm/llm；llm-deepseek；llm-deepseek-api-key；llm-retry。

把 provider 当成 Agent/模型本身；它只是 API 适配层。

项目架构

从 CLI / Desktop 入口画到插件树、Host、Session 与工具执行

目标：能在白板上画出“从命令/窗口到模型请求和工具执行”的完整路径，并判断一个新需求应该落在哪个扩展点。

1. 五个心智模型

先记住这五句话，后面所有细节都挂在它们下面：

  1. 一切皆插件：没有需要打补丁的“特权内核”；服务、工具、UI、持久化都可替换。
  2. 组合是分层的：base bundle → 载体 bundle → profile patch → 用户 patch → 命令行 overlay，后写覆盖同 id 行。
  3. Host 跑树，Client 做投影：Node Host 运行 Cordis 插件树和 Session；浏览器/Electron 只消费 HTTP/WS 与事件投影。
  4. 日志是事实源：Session 事件日志 append-only；模型消息、工具历史、UI 状态都能从日志重建。
  5. 平台载体很薄：Web、Desktop、CLI、SDK、ACP 都是同一套 base + 不同载体 bundle；Linux 移植主要是补发布链，不是重写核心。

4. 启动路径 A：CLI

用户输入 dsh --profile web
  -> apps/cli/src/bin.ts: runCli()
  -> parseDshArgs() 选择 mode=profile
  -> apps/cli/src/profile-boot.ts: runProfile()
  -> packages/boot/app-boot: loadLayeredEnv / loadProfile / Loader
  -> 读取 profile 的 package.json + bundles
  -> 合并 bundle patches + profile patch + user patch + --patch
  -> Loader 激活插件，等待服务可用
  -> web bundle 绑定 webServer，开始监听

关键点：

  • runCli 只做分发；真正的 profile 启动在 profile-boot.ts。
  • dump-config 也走同一套 profile 解析，只是不激活整棵树；它是你验证“装配结果”的第一工具。
  • Loader 是服务可用性驱动的：配置文件里的行顺序不是启动顺序，插件通过 inject 声明依赖。

5. 启动路径 B：Desktop

Electron main (apps/desktop/src/main.ts)
  -> 创建 BrowserWindow，加载 dsh-app://app/
  -> spawn Desktop Host (ELECTRON_RUN_AS_NODE=1)
  -> apps/desktop-host/src/index.ts
  -> 复用 profile runner 加载 desktop profile
  -> base + web-app + desktop 专属 patch
  -> Web Host 监听 127.0.0.1 随机端口
  -> Host 通过 Node IPC 发 boot/ready（端口、token、cookie）
  -> 页面用这些信息连接 /api 与 WebSocket

关键点：

  • Electron main 不跑插件树；它是窗口/菜单/协议/目录选择的外壳。
  • Desktop Host 是 Node 进程，不是浏览器；它和 Web Host 是“同一个 Host 的桌面载体”。
  • 页面加载的是打包后的 Web 前端，但它仍然通过 HTTP/WS 和 Host 通信，不存在“桌面专属 Agent Loop”。

6. Profile 如何装配

一个 profile 至少包含：

  • package.json：dsh.profile.bundles 指定有序 bundle 列表。
  • cordis.patch.yml：该 profile 的覆盖层。

一个 bundle 包包含：

  • package.json 的 dsh.bundle 指向 patch 文件。
  • patch 文件里是一组 Cordis 行（insert/update/remove）。

装配顺序：

  1. 按 dsh.profile.bundles 顺序应用每个 bundle 的 patch。
  2. 应用 profile 自己的 cordis.patch.yml。
  3. 应用 $DSH_HOME/cordis.patch.yml。
  4. 应用命令行 --patch。

同 id 的行，后面的层覆盖前面的层。覆盖是整段 config 替换，不是深合并；所以每个覆盖层必须写出它负责的完整配置。

例子：base 里有一行 id: tools，web-app 里可能再次出现 id: tools 来改 mode；最终只有一行生效，值来自最后一个包含该行的层。

7. 一次 Turn 的数据流

turn/start
  claim inbox: 取 queued message / next-step input
  assemble: system prompt sections + tool schemas
  agent/pre-step
  step/start
  agent/request -> prepareCall
  append user/message; log request/header
  llm/stream -> assistant stream chunks
  assistant/message | assistant/attempt
  tool/call*
    tools/pre-execute
    tools/execute
    tools/post-execute
  tool/result*
  step/end
  有工具结果或新输入 -> 下一个 step
turn/end

需要记住的三条不变式：

  1. turn/start 与 turn/end 成对；step/start 与 step/end 成对；取消/失败也要走收尾事件。
  2. 模型请求头记录实际 provider/model、reasoning effort、max tokens；重放不能靠“当前默认值”猜。
  3. 工具失败通常是一个 tool/result（isError），不是把整个 turn 直接炸掉；只有无法继续的请求/持久化错误才结束 turn。

8. Host 与 Client 的边界

Host 负责：

  • 插件树、Agent、Session、工具执行、模型调用。
  • HTTP API、WebSocket 事件、静态前端资源。
  • 认证 cookie、loopback/trusted host 校验。
  • 把 Session 事件投影成 Client 可消费的 envelope。

3. 代码走读 1：CLI 只是分发器

apps/cli/src/bin.ts 的 runCli 按 mode 分发：

switch (invocation.mode) {
  case 'profile': {
    const { runProfile } = await import('./profile-boot.ts')
    await runProfile({ ... })
    break
  }
  case 'plugin':
    process.exit(await runPlugin(...))
    break
  case 'dump-config':
    runDumpConfig(...)
    break
}

要点：

  • 参数解析和 profile 启动分开；runCli 不持有 Agent/Session。
  • 动态 import 让不相关的命令不必加载整个 Web/Desktop 依赖。
  • dump-config 和真正运行共用 profile 解析，因此它是可信的装配观察点。
  • 默认分支用 satisfies never 做穷尽检查；新增 mode 时编译器会提醒。

4. 代码走读 2：Bundle 是一组可覆盖的行

packages/bundle/base/cordis.patch.yml 用 insert 声明共享服务：

- insert:
    - id: llm
      name: '@deepseek-ai/dsh-llm'

    - id: session
      name: '@deepseek-ai/dsh-session'

    - id: tools
      name: '@deepseek-ai/dsh-tools'

Web 载体在 packages/bundle/web-app/cordis.patch.yml 里用同一个 id 覆盖配置：

- id: tools
  config:
    mode: !!js process.env.DSH_TOOLS_MODE

要点：

  • !!js 是 Loader 的表达式，不是普通 YAML；它会在合适时机求值。
  • 行顺序不是加载顺序；插件靠 inject 等待服务。
  • 覆盖是整段 config 替换；要保留 base 的字段必须重写全部字段。
  • 新工具通常只需要在某个 bundle 里 insert 一行，不需要改 loop。

5. 代码走读 3：工具包长什么样

packages/fs/tool-fs/src/index.ts 的插件形态：

export const name = 'tool-fs'
export const inject = ['tools', 'fs', 'systemPrompt', 'workingDirectory']
export interface Config { read?: boolean; write?: boolean; /* ... */ }
export const Config = z.object({ /* defaults */ })
export function apply(ctx: Context, config: Config): void {
  // 校验 config，然后 applyReadTool/applyWriteTool/...
}

工具注册本身用 defineTool（见 packages/core/tools/README.md）：

ctx.tools.register(defineTool({
  name: 'read_file',
  description: 'Read a file from disk.',
  parameters: {
    path: { type: 'string', required: true },
    offset: { type: 'number' },
  },
  output: {
    schema: { type: 'string' },
    render: (_args, value) => [{ type: 'text', text: value }],
  },
  async execute(args, exec) {
    return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
  },
}))

要点：

  • 工具包只声明“模型能做什么”，具体文件后端是 ctx.fs；这就是 Definition/Provider/Consumer 的分层。
  • parameters 同时是模型 schema 和运行时校验来源；不要手写第二份。
  • execute 只返回声明的 canonical value；UI 展示由 output.render/presentation 负责。
  • 工具失败应返回结构化错误结果，不要用异常结束整个 turn，除非无法继续。

6. 代码走读 4：Agent Loop 的 turn/step

packages/core/agent-loop/src/agent.ts 里核心是 kick() → turn() → step()：

  • kick()：在空闲时唤醒驱动，处理 inbox 中的输入。
  • turn()：建立 turn/start/turn/end，循环执行 step，直到完成/取消/失败。
  • step()：组装 prompt/tool schema，调用 LLM，处理 assistant 流和工具调用。
  • prepareRequest() / buildRequest()：把 Session 日志中可重建的上下文变成实际请求。
  • toolsChanged()：工具集变化会影响 prompt，需要重新组装。

一个 step 结束不等于 turn 结束：工具结果可能需要再请求模型；因此 loop 会根据“是否还有工具要执行/是否有新输入”决定是否进入下一个 step。

读这段时只问三个问题：

  1. 这个函数在哪个事件边界内运行？
  2. 它追加了哪些 Session 事件？
  3. 它什么时候让出控制权给下一个 step/turn？

7. 代码走读 5：Session 事件是声明合并的

packages/core/session/src/types.ts 定义基础事件；其他包通过 declaration merging 增加事件类型。例如 tools 包在 packages/core/tools/src/types.ts 里扩展 SessionEventMap：

declare module '@deepseek-ai/dsh-session/types' {
  interface SessionEventMap {
    'tool/ptc-dispatch-start': PtcDispatchStartEventData
    'tool/ptc-dispatch': PtcDispatchEventData
  }
}

要点：

  • 事件 payload 是持久化数据，必须能用 JSON 表达；不要塞函数、类实例、循环引用。
  • 日志专用事件（log-only）不会进入 deriveMessages()，因此不会重新变成模型上下文。
  • 想让模型看到的新输入，必须同时设计它的事件和 deriveMessages 的读取路径；否则重放会丢。
  • 事件监听器用 ctx.on 注册，返回 disposer；插件卸载后不能继续写日志。

8. 代码走读 6：Desktop 与 Desktop Host

模块 2：架构

练习题要点

  1. 命令 → args → profile-boot → app-boot/Loader → profile+bundles+patches → web bundle 激活 → webServer 监听。
  2. Electron main → 创建 BrowserWindow → spawn Desktop Host → 加载 desktop profile → Web Host 监听 → IPC boot/ready → 页面连接 API/WS → 首次渲染。
  3. 示例：工具=输入 schema、输出 canonical value、测试注册+执行+dispose；provider=输入请求、输出流、测试 mock/真实 API；client UI=输入投影、输出组件、测试 slot 注册/卸载。

模块 3：代码

自测

  1. 动态 import 让未用到的命令不加载重依赖；会影响启动路径，但按 mode 分摊。
  2. inject 决定依赖和服务可用性；行顺序不决定激活顺序。
